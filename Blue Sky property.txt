## 🏗️ Blue Sky Property Management — System Architecture v1

I'd structure the system around **four major domains**:

```text
                         BLUE SKY PLATFORM
                                │
       ┌────────────────────────┼────────────────────────┐
       │                        │                        │
   PROPERTY SIDE           RENTAL SIDE              PLATFORM
       │                        │                        │
   Providers                 Applicants              Admin
   Properties                Applications            Settings
   Listings                  Documents               Payments
   Units                     Payments                Messages
```

### The important principle

There are **three different people/entities** we must not mix together:

1. **Admin** — controls the platform
2. **Property Provider** — owner/agent who lists property
3. **Applicant/Tenant** — person looking to rent

A provider can submit properties.

An applicant can apply for properties.

Admin controls verification between both.

### `profiles`

| Field        | Purpose                      |
| ------------ | ---------------------------- |
| `id`         | User ID                      |
| `email`      | Login email                  |

| `full_name`  | User name                    |
| `role`       | admin / provider / applicant |
| `status`     | active / suspended           |
| `created_at` | Registration date            |

If we're using Supabase, authentication itself should live in **Supabase Auth**, while `profiles` stores the application's user information.

And **role authorization should not simply depend on editable frontend/user metadata**. We'll enforce it server/database-side.

# ⏰ What happens when the period expires?

This is where we need to be clever.

We **shouldn't physically delete or permanently reject the properties**.

Their property records remain.

Instead, public visibility becomes conditional:

```text
Property approved
        AND
Provider has active listing period
        ↓
      PUBLIC
```

If:

```text
expires_at < NOW()
```

then:

```text
NOT PUBLIC
```

The property remains in the provider's dashboard.

So the provider sees:

> **Your listing access expired on November 18. Renew to republish your properties.**

That's much better than deleting anything.

# 🟢 Renewal

Suppose John renews on December 1.

He pays for another 90 days.

A new:

`provider_listing_period`

is created.

```text
Period #1
Aug 20 → Nov 18
EXPIRED


Period #2
Dec 1 → Feb 28
ACTIVE
```

His previously approved properties can become visible again.

We don't need him to upload everything again.

---

# One subtle issue: what if he renews before expiry?

We should support that too.

Example:

```text
Current period:
Aug 20 → Nov 18
```

John renews on:

**Nov 10**

We shouldn't make his new period:

```text
Nov 10 → Feb 7
```

because he'd lose eight days.

Instead:

```text
Current:
Aug 20 → Nov 18

Renewal:
Nov 19 → Feb 16
```

So the system should calculate:

```text
new_start =
    current_active_period.expires_at
```

when renewing early.

That gives providers the full value they paid for.

# 10. Renewal behavior

We should explicitly encode this rule:

### Early renewal

If current access expires on:

> November 30

and provider renews on:

> November 10

the new period begins:

> December 1

—not November 10.

That prevents providers from losing unused days.

Conceptually:

```text
current_period.expires_at
        ↓
new_period.starts_at
```

If there is no active period:

```text
new_period.starts_at = payment verification time
```

# ⚡ The provider expiration engine

One more architectural point.

We **don't need to constantly update every property** when a provider's period expires.

Instead, public-property queries check:

```text
property approved
+
provider has active listing period
+
expires_at > current time
```

That means expiration happens naturally.

For notifications, however, we'll eventually need a scheduled process that checks:

```text
30 days remaining
14 days
7 days
3 days
1 day
expired
```

That can be handled later with a scheduled backend job.

# 🎨 Design system direction

Before we generate the actual images, I'd define the visual direction.

Blue Sky should **not** look like another generic Nigerian property website with a blue navbar, random stock photos, and 47 shadows fighting for their lives. 😂

### Brand personality

**Trustworthy + modern + calm + premium + accessible.**

Think:

> "Professional property management company"

rather than:

> "Random real-estate listing site."

### Visual priorities

**1. Property photography**

The property itself should dominate.

**2. Trust signals**

Verified badges, transparent status, clear information.

**3. Clean typography**

Large readable headings, excellent spacing.

**4. Cards**

Property cards should be highly visual but compact enough for mobile.

**5. Minimal color palette**

Use the Blue Sky brand colors established from the logo, with neutral backgrounds.

**6. Strong CTAs**

Especially:

* Apply
* Message
* Search
* Add Property
* Renew Listing Access

---

# 📐 Mobile-first design rules

This should be our design law:

### Don't design desktop and shrink it.

Instead:

```text
Mobile
  ↓
Tablet
  ↓
Desktop
```

### Forms

One-column by default.

### Cards

Vertical on mobile.

### Tables

Never force wide tables onto mobile.

Use:

```text
Card
→ tap
→ details
```

### Admin

Dense information can become:

```text
Metric cards
↓
Filter
↓
Record cards
↓
Details
```

### Bottom navigation

Use it where it improves frequent mobile workflows.

### Sticky actions

For critical actions:

```text
[ Apply Now ]
```

should remain easy to reach.

## And one important rule

**We should not generate the final visual design yet.**

We're almost there, but before I trigger image generation, I would lock **three things**:

1. **Exact user flows** — especially provider payment → listing access → property publishing and applicant → application → verification.
2. **Wireframe structure** — what appears above/below the fold on each major screen.
3. **Brand/design direction** — Blue Sky's colors, typography, photography style, card style, buttons, navigation, and overall visual language.

Once those three are locked, **then we generate the five design boards**. That will give us a coherent product instead of a collection of beautiful screenshots that don't actually fit together.

All right, so now let's look those three things, the exact user flows, the wireframe structure, and brand design direction for BlueSky, so we can move to generating the images of those pages. So, and also for the route, admin should be able to upload listings. I just thought you should know that. So yeah, that is all.
Yep. And that last detail matters: **Admin is also a property publisher**, so the property workflow shouldn't be provider-only. Admin can create/upload listings directly, bypassing provider listing-access requirements.

Let's lock the three things now: **user flows → wireframe rules → visual direction.**

# 3. Blue Sky Brand / Visual Direction

Now the fun part.

## Brand personality

Blue Sky should communicate:

**Trust**

**Clarity**

**Safety**

**Professionalism**

**Modern property management**

**Accessibility**

Not overly corporate.

Not flashy.

Not "crypto startup real estate." 😂

---

# Color direction

The existing Blue Sky identity should drive the palette.

I'd use:

### Primary

**Blue**

For:

* CTAs
* links
* active states
* verification indicators
* navigation accents

### Sky / light blue

For:

* subtle backgrounds
* information cards
* highlights

### Deep navy

For:

* headings
* navigation
* important text

### Neutral

White / very light gray backgrounds.

### Status colors

Green:

**Verified / Approved / Active**

Amber:

**Pending / Warning**

Red:

**Rejected / Expired / Error**

But status colors should remain secondary to the brand blue.

---

# Typography

We want something modern and extremely readable.

I'd go with a clean sans-serif family such as:

**Inter** or **Plus Jakarta Sans**.

My preference:

### Headings

**Plus Jakarta Sans**

### Body/UI

**Inter**

That gives Blue Sky a polished property-tech feel without becoming unnecessarily fancy.

---

# Property photography

This is **critical**.

Use:

* bright natural lighting
* realistic Nigerian residential environments where possible
* clean interiors
* wide-angle architectural photography
* no cheesy handshake photos
* no fake smiling "agent pointing at house" stock photography

The property is the hero.

---

# UI style

### Cards

Moderate radius.

Not:

> `border-radius: 40px` everywhere.

Something around:

**12–16px**

### Shadows

Very subtle.

### Buttons

Solid primary blue for important actions.

Secondary buttons:

Outlined / neutral.

### Inputs

Large touch targets.

Minimum roughly:

**44–48px height**

because this is mobile-first.

---

# Verification visual language

This should become one of Blue Sky's signature design elements.

Example:

```text
✓ Verified Property
```

But don't just slap a blue badge everywhere.

Verification should appear consistently:

```text
✓ Verified Property
✓ Verified Provider
✓ Payment Verified
✓ Identity Verified
```

The user should immediately understand what has actually been verified.

---

Every property screen should follow:

The user shouldn't need to hunt for:

or:
